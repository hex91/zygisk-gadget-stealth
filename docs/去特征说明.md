# 去特征说明与实测

> 结论先说：本项目把常见检测面（maps 路径、线程名、logcat、TCP 端口、已知文件名）都处理了，但**没有**改 frida-gadget 本体，所以 linker solist、匿名可执行段、Gum 引擎内存特征仍在。不要把它当成「过所有检测」。

## 检测面清单

| # | 检测点 | 原版 ZygiskFrida | 本项目 | 实现位置 |
|---|---|---|---|---|
| 1 | `/proc/<pid>/maps` 里的 so 路径 | 已匿名化 | 匿名化 + 中性文件名 | `native/stealth.cpp: remap_library` |
| 2 | 已知路径 `re.zyg.fri` | 会出现 | 换成 `.gsys`，可自定义 | `customize.sh` + `gadget_ctl.sh datadir` |
| 3 | 已知文件名 `libgadget.so` | 会出现 | `libgcore.so` / `libgcore32.so` | `settings.conf` |
| 4 | 线程名 `gum-js-loop` / `frida-gadget` / `gmain` / `gdbus` | 残留 | 持续伪装成真实 ART/App 线程名 | `native/stealth.cpp: start_thread_cloak` |
| 5 | logcat `ZygiskFrida: App detected: <pkg>` | 会打印 | 默认完全静默 | `no_log=1` + `gs_log` 空操作 |
| 6 | TCP 监听端口、`/proc/net/tcp` | listen 默认 27042 | 默认 `script` 模式零端口 | `settings.conf: mode` |
| 7 | ptrace / APK 签名 / 完整性校验 | 不涉及 | 不涉及 | Zygisk 方案固有 |
| 8 | 非目标进程里的模块 so | 会卸载 | 立即 `DLCLOSE_MODULE_LIBRARY` | `native/main.cpp` |
| 9 | 注入时机扫描 | 可配延迟 | 默认 1200ms + 每目标可覆盖 | `delay_ms` |

### 各项实现细节

**maps 匿名化**：`dlopen` 成功后解析 `/proc/self/maps`，把含 `lib_name` 的每一段 `mmap` 匿名内存 → 复制 → `mremap(MREMAP_FIXED)` 覆盖原地址 → 恢复原保护位。文件路径从 maps 里消失，代码地址不变所以不影响运行。思路来自 ZygiskFrida 的 `remapper.cpp`（MIT）。

**线程伪装**：注入后起一个低频守护线程，前 10 秒每 100ms、之后每 1 秒扫描 `/proc/self/task/*/comm`，发现含 `frida` / `gadget` / `gum-` / `gmain` / `gdbus` / `gjs` 的名字就写回中性名。`thread_alias=auto` 时从下面这组真实线程名轮换：

```
pool-2-thread-1/2/3, ReferenceQueueD, FinalizerWatchd,
hwuiTask2, SurfaceSyncGrou, AsyncTask #3
```

守护线程自己叫 `pool-2-thread-9`。之所以要**持续**扫描：gadget 内部可能再次 `prctl(PR_SET_NAME)` 把名字设回去。

**静默日志**：native 侧所有日志走 `gs_log()`，`no_log=1` 时是空操作，编译也不链接任何调试输出。注意：如果设备上还装着原版 ZygiskFrida，它**仍会**打印 `App detected`，与本模块无关；要彻底清掉请卸载旧模块。

**零端口**：`script` 模式下 gadget 直接加载本地 js，不进入 listen 交互，因此 `/proc/net/tcp` 里没有 gadget 条目。开发期可临时切 `listen`（端口 27052 + `on_load=resume`），稳定后切回。

## 真机实测数据

环境：Pixel 6 (oriole) / Android 15 / KernelSU + Zygisk Next 1.5.2 / SukiSU 4.1.0，目标 `com.hex91.appinspector`，gadget 官方 17.5.2 arm64。

### script 模式（默认）

```
状态文件 : ok=1;pkg=com.hex91.appinspector;pid=9190;mode=script;
           lib=libgcore.so;gver=17.5.2;abi=arm64;maps=1;threads=1;detail=xdl
脚本证据 : pid=9190 frida=17.5.2 arch=arm64 modules=338
监听端口 : 只有 frida-server 的 39527，无 gadget 端口
```

`/proc/<pid>/maps`（2826 行）：

```
gadget=0  frida=0  libgcore=0  .gsys=0  module_id=0  re.zyg.fri=0
```

线程名（grep `frida|gadget|gum-|gmain|gdbus`）：**0 个**。被改名的 3 个显示为 `pool-2-thread-1/2/3`，守护线程 `pool-2-thread-9`。

logcat 中本模块 tag `gs`：**0 行**。

### listen 模式（对照）

```
27052 监听者 = com.hex91.appinspector 本身
frida-ps -H 127.0.0.1:27052  ->  9863  Gadget
脚本返回  -> {'ver':'17.5.2','arch':'arm64','platform':'linux','pid':9863,'modules':338}
frida-ps -H 127.0.0.1:39527  ->  整机进程正常（server 共存）
```

### 与原版 ZygiskFrida 的对照

原版（同一设备、同一 App、17.4.0 gadget）实测：maps 里 `gadget/frida/re.zyg.fri` 也是 0（它的 remapper 同样有效），但线程名残留 `frida-gadget`、`gum-js-loop`、`gmain`、`gdbus` 各 1 个，logcat 有 `ZygiskFrida: App detected`，且 listen 模式有 27052 端口。本项目把这三处都补掉了，并把 gadget 从 17.4.0 换成与 PC 一致的 17.5.2。

## 仍然存在的检测面（不承诺消除）

1. **linker solist**：`dlopen` 后 linker 内部仍记录 so 名，用 xDL 之类遍历 linker 的反检测能看到；maps 匿名化只抹 `/proc/maps`。
2. **匿名 RX 段**：重映射后表现为来源不明的匿名可执行段，高级检测会按「匿名 r-xp + 大体积」判可疑。实测目标进程有 4 个 `r-xp 00000000` 段。
3. **Gum / GLib 内存特征**：线程名只是 `comm`，JS 引擎的堆布局、`frida` 相关字符串常量仍在内存里。
4. **状态与证据文件**：`write_state=1` 会留 `.gs_state.<pid>`；默认 `hook.js` 会留 `gs_proof.txt`。正式部署可把这两处关掉/删掉。
5. **listen 模式**必然有端口，谈不上零端口。
6. **Zygisk 本身**：强反检测会查 Zygisk 模块列表、`/data/adb/modules`、zygote 注入痕迹，本模块无法覆盖。

彻底消除 1–3 需要从 frida 源码层改写 gadget 并自行编译，本项目不做。

## 使用建议

1. 稳定 hook 一律 `script`；开发期才切 `listen`。
2. `delay_ms` 设 500–3000，避开启动期扫描。
3. 目标白名单只填真正需要的 App，别全量注入。
4. **不要**用 frida-server 再 attach 已加载 gadget 的进程 —— 两份 Gum 在同一地址做 inline hook 会互相覆盖，可能崩溃或整机重启。
5. 若目标是尽量小的整机特征，可在另一个仓库的 WebUI 里关掉 frida-server 开机自启，只留 gadget。
6. 状态文件和 `gs_proof.txt` 是调试辅助，正式部署按需关闭。
7. 仅限自有设备或已授权目标的研究用途。
